## 結論

Phase 2 已完成：計算引擎、Repository 抽象、完整備份、嚴格匯入驗證、IndexedDB 升級／損壞復原、里程碑紀錄語意與統一捨入規則皆有可重現測試。因沒有業主確認的正式預算書，黃金資料定位為內部回歸基準，不代表外部預算書驗收。

## 現有保護

- 計算核心為純函式，火警範例案固定驗證 `815.417 工 / 2,446,251 元`。
- `CaseRepository` 與 `MasterRepository` 隔離 IndexedDB，上層不直接存取資料庫。
- Case Repository 以同一組合約測試驗證記憶體與 IndexedDB 實作。
- IndexedDB schema 目前為 v2，包含 `cases`、`meta`、`customItems`。
- 舊案件開啟時會補欄位並遷移舊工項碼；匯入同編號案件會改名，避免覆蓋既有案件。
- 14 個測試檔、134 項單元／整合測試與 12 項 E2E 提供現行回歸基準。

## 主要缺口與風險

### 已處理：備份不完整

v2 `CaseBackup` 會匯出案件及該案件實際引用的 `customItems`；匯入支援 v1 相容讀取，並先分類新增、相同與衝突工項。衝突資料只有在使用者明確確認後才會覆寫，Repository 以單一 IndexedDB transaction 批次寫入自訂工項。

驗證證據：單元測試確認只攜帶被引用工項且匯入前後計算總額一致；Playwright 在全新瀏覽器資料庫完成匯出、匯入及主檔還原。

### 已處理：備份版本與結構驗證不足

匯入只接受 v1／v2，並逐層驗證 envelope、`Case`、`VersionRecord`、`LineItem`、系統鍵、自訂子系統與 v2 自訂工項。數值須為有限且非負，檔位與分類須在允許集合內，重複列 id、重複自訂碼及缺少被引用自訂工項都會在 Repository 寫入前被拒絕；錯誤訊息包含欄位路徑。

相容策略：v1 可缺少後加入的 `customSystems` 與 `LineItem.spec`，匯入時補為安全預設；不支援版本會直接停止。負向測試涵蓋錯誤型別、負數、非法檔位、未知系統鍵、重複 id、自訂碼與引用完整性。

### 已處理：IndexedDB 升級與損壞復原未驗證

真實 v1 fixture 會升級至 v2、保留既有案件並建立空的 `customItems` store。`SeedMasterRepository.readCustom()` 現在只在確實為空時回傳空陣列；schema 缺損或讀取錯誤會中止初始化並顯示復原畫面，不再把故障偽裝成沒有自訂工項。

復原畫面先提供重試；重建按鈕明確警告會永久刪除本瀏覽器案件與自訂工項，要求使用者僅在已有 JSON 備份或確定放棄資料時確認。新版分頁會在版本變更時自動釋放連線；舊分頁仍占用時，單一刪除要求會等待解除占用，避免重複排程。單元測試與 Playwright 均驗證重建後使用最新 schema 並可重新啟動。

### 已決定：版本紀錄定位為里程碑稽核標記

`versions[]` 只保存版本號、時間與備註，並沒有保存案件內容，因此不能還原至歷史版本。UI 文案應避免讓使用者誤以為這是可回復版本。

產品決策採「僅稽核標記」：畫面統一稱為「里程碑紀錄」，明示不保存案件內容且無法還原；新增紀錄只遞增里程碑編號並保存時間與備註。既有 `version`／`versions[]` 欄位維持不變，以相容舊案件與備份。E2E 驗證提示文案與新增紀錄流程。

### P2：刪除與本機儲存風險

案件刪除只有確認視窗，沒有刪除前備份或回收區；所有資料仍受單一瀏覽器 profile、清除網站資料及裝置故障影響。

完成條件：在正式單機版發布前加入備份提醒、最後備份時間提示與可測試的復原說明。
