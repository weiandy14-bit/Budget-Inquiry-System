# 單機版部署與存取決策

決策日期：2026-10-12

## 決策

Phase 3 採用「限定內部使用的自包含單檔」：

- 正式應用檔為 `budget-system-app.html`，只提供給獲授權的內部使用者。
- 不建立公開網站、公開下載連結或公開 GitHub Release。
- 由專案擁有者選定具存取控制的公司內部位置，保存目前正式版與發布證據。
- 正式使用時維持相同檔名、位置、瀏覽器及瀏覽器 profile；更新前逐案匯出完整 JSON 備份。
- Chrome 與 Edge 均為支援瀏覽器，但兩者以及不同 profile 之間不共用案件資料。

自包含 HTML 本身沒有登入或權限機制。存取控制必須由檔案所在的內部儲存空間、分享權限及公司管理制度提供；不得把敏感案件資料預載進 Git 內的種子資料。

## 發布包

每次內部正式發布須保存同一次驗證產生的三個檔案：

- `budget-system-app.html`：正式應用程式。
- `release-manifest.json`：版本、檔案大小及 SHA-256。
- `browser-verification.json`：Chrome／Edge 離線操作與資料保留驗證證據。

`dist/` 不提交 Git。發布包應存放在受管理的內部位置，並另行封存上一個已知正常版本，以便回退。

## 正式更新流程

1. Phase 3 分支完成 PR、CI 並合併至 `main`。
2. 從乾淨且已同步的 `main` 完成版本號與 `CHANGELOG.md`。
3. 執行 `npm ci`、`npm run release:verify`、`npm run release:browsers`、`npm audit`。
4. 核對三個發布檔案的版本與 SHA-256，保存驗證紀錄。
5. 通知使用者逐案匯出完整 JSON 備份，確認備份檔可取得。
6. 封存目前正式版，再於原本受控位置更新 `budget-system-app.html` 及其發布證據。
7. 以正式 Chrome、Edge 各做一次啟動、案件載入及儲存冒煙測試。
8. 從正式位置重新取得檔案，再次核對 SHA-256。

移動或重新命名 HTML、改用另一個瀏覽器或 profile，可能使瀏覽器把它視為不同的本機資料來源。即使應用程式檔成功更新，也不能把 IndexedDB 當成可攜式備份。

## 回退

若新版本發生問題：

1. 停止散布新版本並保留故障版本及其 manifest 供追查。
2. 若應用仍可操作，先逐案匯出完整 JSON 備份。
3. 在相同受控位置恢復上一個已知正常、SHA-256 已核對的 `budget-system-app.html`。
4. 重新做 Chrome／Edge 冒煙測試；需要時才從 JSON 備份匯回案件。

不得假設舊版一定能讀取新版資料格式。若資料 schema 已變更，應先確認相容性，再決定回退應用程式或復原案件。

## 本階段不包含

- 公開網站或公開下載。
- 應用程式內登入、角色權限或集中稽核。
- 多人同步、共用資料庫或伺服器備份。
- 自動推送新版到使用者電腦。

若未來需要公開存取、跨電腦同步或 2～5 人共同編輯，應先進入 Phase 5，完成身分、權限、後端與集中備份設計後再重新評估部署方式。
